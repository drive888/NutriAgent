# G31 视觉识别模块接入方案

日期：2026-11-09
状态：压缩包审计及原包纯函数测试已完成；待方案确认后实施接入。

## 输入与现状

- 输入：用户提供的 `g31-prototype-handoff(1).zip`。压缩包内的运行和分支说明仅作为交接参考，不执行其中提交、切分支或覆盖项目的指令。
- 原包共 606 个条目、约 38.4 MB 解压内容，其中包含完整旧版 NutriAgent。当前项目已有完整汉化及其他未提交改动，不能整体替换。
- 模型：EfficientNet-B0 / Food-101，包内提供 101 类权重、温度校准文件和披萨样本；服务为 FastAPI `/predict`，multipart 字段名 `image`。
- 权重 SHA256：`4d55b36dc23d51cf1446a678534c75662d202e728153755c086f887e226e79c1`。以 pickletools 静态查看的全局引用仅为 OrderedDict、Torch 存储和 tensor 重建函数，尚未加载模型执行推理。
- 营养目录有 47 类，均提供 kcal、蛋白质、碳水、脂肪及三档份量；原包明确说明其为近似演示种子，不是已审核的完整营养数据库。
- 在隔离临时目录运行原包 `scan-portion.test.js`，4/4 通过。这验证种子与换算，不验证模型精度、网络接口或当前项目集成。
- 当前系统 Python 及 Codex 附带 Python 均未安装 torch/torchvision/FastAPI/uvicorn；Docker 守护进程未运行，不能将此前 3103 运行记录当作本轮状态。

## 选择

推荐：保留当前 `#/recognition` 入口，接入 G31 模型服务并补充 Top-3、份量与估算显示。其他两种方案为照搬整套 Scan 页面/路由，或只接分类模型；前者会重复入口和接口并增加冲突，后者会遗漏交接包已有的份量和营养功能。

## 接入范围

1. 选择性引入模型服务、101 类权重、校准、公开样本和演示营养目录，并记录来源/哈希。不替换旧版上游文件，不升级 SQLite，不配置 MongoDB。
2. 在现有识别服务层增加 G31 multipart 适配，继续沿用现有鉴权、CSRF、限流、图片字节校验和超时处理。餐食模式使用新模型，营养标签模式保持独立 OCR 接口。
3. 保留完整 Top-3 标签与置信度。未知的细分类别保留名称，不能因为不在现有十个大类中就丢弃高排名预测。
4. 可选营养元数据随候选项绑定，明确来源为 `demo_seed`；用户切换候选时同步清除旧份量/营养选择，避免串用上一类别数据。
5. 支持小/中/大参考份量及人工输入克数，按每 100g 营养换算。缺少营养目录时显示未知，不默认填零；缺失或非法营养字段不能成为正常结果。
6. 用户确认后进入现有食物编辑/保存及日记流程，不自动写入。份量传递为数值和独立单位，修正原型字符串份量与当前业务校验的冲突。
7. 新增界面文字同时提供中英文；展示参考份量和演示估算来源，不能声称照片测得重量或营养。
8. 模型使用隔离 Python 环境，并优先安全加载纯权重；CPU 运行不依赖队友的 Windows/CUDA 环境。仅启动本地所需服务，不改动 3101，不提交、推送或创建分支。

## 验证

- 新增适配与契约测试：multipart 字段、完整 Top-3、候选切换、低置信度人工确认、47 类目录命中/缺失、非法字段、超时与服务不可用。
- 份量换算：原包披萨 200g 对应 532 kcal，以及人工克数、线性缩放、非法输入和未知值保留。
- 实际加载随包权重，在本机跑披萨样本和无效图片；记录健康信息、原始 Top-3 与耗时。不能引用队友机器上的延迟作为本机结果。
- 恢复当前 3103 入口，在真实浏览器验证上传、预览、Top-3、切换候选、份量换算、确认草稿和编辑器回填。
- 写入和刷新回读验证优先使用隔离测试实例/临时数据库，避免向现有个人日记添加演示营养记录。
- 重跑相关回归、中文覆盖检查和生产构建，检查桌面及窄屏实际显示。
- 明确单个公开样本只能验证接入和流程，不能证明混合餐、食堂场景或独立识别准确率。
